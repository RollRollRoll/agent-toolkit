# Prototype

原型是**用来回答一个问题的一次性代码**。**问题决定形状。**

## 选分支

从用户的话、周围的代码，或者（用户在的话）直接问，判断现在要回答的是哪个问题：

- **「这套逻辑 / 状态模型对味吗？」** → [references/logic.md](references/logic.md)。
  做一个**可分享的单个 HTML 文件**（自由点按钮 + 分页签的引导演练），
  把状态机推过那些在纸上想不清楚的情况，而且**非开发者也能自己驱动**。
- **「这东西该长什么样？」** → [references/ui.md](references/ui.md)。
  在**同一条路由**上生成**几个根本不同**的界面变体，用一个 URL search 参数
  加一条悬浮底栏来切换。

两条分支产出的东西**完全不同**，所以**选错就浪费掉整个原型**。如果问题真的两可、
用户又联系不上，就按周围的代码来选（后端模块 → 逻辑；页面或组件 → 界面），
并**把这个假设写在原型顶部**。

## 两条分支都适用的规则

1. **从第一天起就是一次性的，而且要明确标出来。** 把原型代码**放在它真正会被用到的地方附近**
   （挨着它在为之做原型的那个模块或页面），让上下文一目了然；但**名字要让随便一个读者
   一眼看出这是原型、不是生产代码**。一次性的 UI 路由要**沿用项目已有的路由约定**，
   不要自己发明一套新的顶层结构。
2. **跑起来要毫不费力。** UI 原型要能从项目任务运行器里的**一条命令**起来：
   `pnpm <name>`、`python <path>`、`bun <path>` 等等。逻辑演示则是**用户双击就能打开的
   单个 HTML 文件**。总之，**启动它不需要动脑子**。
3. **默认不做持久化。** 状态活在内存里。**持久化正是原型要检验的东西**，不该是它依赖的东西。
   如果问题本身就跟数据库有关，那就打一个临时库或本地文件，名字里明确写上
   「PROTOTYPE，随时可删」。
4. **跳过打磨。** 不写测试；错误处理只做到**让原型能跑起来**为止；不做抽象。
   **重点是快速学到东西。**
5. **把状态摊开。** 每次操作之后（逻辑分支）或每次切换变体时（UI 分支），
   **把完整的相关状态打印或渲染出来**，让用户看得见变了什么。
6. **做完要把它留档。** 先把验证过的决策**并回真实代码**，然后把原型本身**当作一手来源存起来**：
   提交到一个**一次性分支**上（不进 main），并在实现 issue 上留一个指向那个分支的上下文指针。
   **答案也要留档**（结论是什么、它解决了哪个问题），写进 issue 或 commit。
   **main 分支只保留那个被验证过的决策。**
