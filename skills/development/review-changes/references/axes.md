# 六关逐项判据 — 每关看什么、什么算过、常见漏判

> 用途：`review-changes` 读完审查包后，按这里逐关判定。每关都要有结论，
> "看着没问题"也要说出依据。

## 一 · correctness（正确）

**看什么**

- 改动实现的行为，与需求依据（spec / design / tasks / 任务描述）说的是不是同一件事。
- 边界：空集合、单元素、极大值、并发、重复调用、部分失败。
- 错误路径：异常被吞了吗？失败时状态一致吗？重试安全吗？
- 数据：迁移可重复执行吗？回滚路径存在吗？

**什么算过**：每条验收标准都能在 diff 里指出落点，边界与错误路径有明确处理（或明确判定不适用）。

**常见漏判**：只看 happy path；把"测试绿了"当成"行为对了"（测试可能本身就是错的，见第六关）。

## 二 · readability（可读）

**看什么**

- 命名说清意图吗（`data`、`tmp`、`handle2` 属于没说清）。
- 函数职责单一吗？嵌套深度、参数个数、隐式约定多不多？
- 复杂逻辑有没有解释**为什么**的注释（解释 what 的注释通常是命名没做好）。

**什么算过**：不熟悉这段代码的人读一遍能说出它在干什么、为什么这么干。

**常见漏判**：把风格偏好当问题报（缩进、引号）；把"我会写得不一样"当成可读性问题。

## 三 · architecture（架构）

**看什么**

- 模块边界与职责：这段逻辑放在这一层对吗？有没有跨层直连、循环依赖？
- 重复：同一决策散落在几处吗？改一处会漏掉另一处吗？
- 耦合：换掉一个实现要动几个文件？测试能不能只针对 seam？
- 调用方给的**执行期疑虑**清单——那是实现方看到但按规则没动的结构问题，优先看这些点。

**什么算过**：边界能一句话说清，重复与耦合都是有意识的取舍而非疏忽。

**常见漏判**：为小改动提出大重构（记 Minor，别当阻塞项）；忽略"临时方案"正在长成主路径。

## 四 · security（安全）

**看什么**

- 输入校验：外部输入到达信任边界前被校验了吗；注入面（SQL / 命令 / 路径 / 模板 / 反序列化）。
- 认证与授权：这个入口该不该有人访问？越权路径存在吗？
- 敏感数据：密钥 / token / 个人信息有没有进日志、进错误信息、进版本库。
- 依赖：新引入的依赖来源可信吗？有没有已知问题？

**什么算过**：改动引入的每个外部入口都有明确的信任边界与校验。

**常见漏判**：只看新代码，忽略改动**放大**了既有漏洞的暴露面；把"内网"当成免检理由。

## 五 · performance（性能）

**看什么**

- 明显热点：循环内 IO、N+1 查询、重复计算、无界缓存 / 无界并发。
- 数据规模：这段代码在真实数据量下还成立吗？
- 资源：连接 / 文件句柄 / 协程有没有关？

**什么算过**：按**项目实际规模**判定——没有明显热点即可，不为想象中的规模提前优化。

**常见漏判**：把微优化报成问题（过早优化）；反过来，放过循环里的数据库查询。

## 六 · 测试质量（唯一关口）

红绿循环里没有 reviewer 审过测试本身，这一关是唯一的关口。**一批全绿的同义反复测试等于没有测试。**

**看什么**

- **同义反复**：期望值是不是按被测代码的同一套算法重算的（`toBe(items.reduce(...))`、
  按同样方式手推的快照、常量等于自己）——它按构造必然通过。
- **实现耦合**：mock 了自己的模块 / 内部协作者？断言"某方法被调用过"？绕过被测接口从侧信道验证？
- **测在哪**：测试住在可观察的 seam 上，还是伸进了私有实现 / 硬测 IO 外壳。
- **覆盖**：边界、错误路径、验收标准里点名的用例，有对应测试吗？
- **红过吗**：调用方给了执行记录时，核每个行为是否都有实现前的失败输出——只有绿没有红，
  说明测试是事后补的。

**什么算过**：把实现改错，至少有一个测试会红；只改结构不改行为，测试仍绿。

**常见漏判**：数测试数量而不看断言内容；看到 mock 就放行。
