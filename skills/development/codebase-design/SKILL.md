# Codebase Design — 深模块设计词汇

## 目标

设计**深模块**：把大量行为藏在一个小接口后面，接口落在一条干净的 seam 上，并且**通过这个接口**就能测。
代码被设计或被重构的任何场合，都用这套词汇和判据。要的是三样东西：

1. **调用方拿到杠杆（leverage）** —— 每学一份接口，能换到更多能力。
2. **维护者拿到局部性（locality）** —— 改动、bug、知识和验证收敛在一处，改一次就到处生效。
3. **所有人拿到可测性** —— 调用方和测试穿过同一条 seam，接口就是测试面。

**刻意止步于此**：本 skill 只提供**设计词汇与判据**——怎么命名、怎么判深浅、seam 该放哪、
一簇浅模块能不能深化、要不要多设计几版接口。它不产出行为规格、不做技术选型决策、
不拆任务、不写实现代码。

> 一句话：**深度是接口的属性，不是实现的属性**。判一个模块好不好，看调用方为了用它必须学多少，
> 而不是看它内部有多少行。

## 调用契约

**传入**

- **设计对象**：要设计或改进的模块 / 一簇模块（给文件路径最好，或直接描述现在的接口与实现）。
- **约束**（可选）：依赖情况、不能动的调用方、测试怎么跑、既有命名约定。
- **想要什么**（可选）：只借词汇统一说法、找深化机会、判 seam 位置，还是要多版接口对比。

**取回**

- **用统一词汇写出的设计判断**：这个模块深还是浅、接口能不能再收窄、seam 应该落在哪、
  哪些依赖要走 port + adapter。
- **深化建议**（若适用）：哪几个模块该合、合完的接口长什么样、测试怎么从旧的挪到新的。
- **多版接口对比**（若要求）：见 [references/design-it-twice.md](references/design-it-twice.md)。
- **推断假设**与**需对方拍板的点**。

**本 skill 不做**

- 不定行为契约、不写需求（那是 write-spec）。
- 不做技术选型与整体架构决策（那是 make-design）。
- 不拆任务、不写实现代码、不做代码审查。

## 术语表

**这些词按字面意思用，不要替换**——不要换成 "component"、"service"、"API"、"boundary"。
词汇统一本身就是目的。

**模块（Module）**：任何有接口和实现的东西。**刻意不限尺度**：一个函数、一个类、一个包，
或一条跨层的纵切片，都叫模块。*避免*：unit、component、service。

**接口（Interface）**：调用方为了**正确使用**这个模块必须知道的**全部事实**——类型签名，
以及不变量、调用顺序约束、错误模式、必需的配置、性能特征。*避免*：API、签名
（太窄，它们只指类型层面的表面）。

**实现（Implementation）**：模块内部的东西，它的代码体。与**适配器**是两回事：
一个东西可以是小适配器 + 大实现（Postgres 仓储），也可以是大适配器 + 小实现（内存 fake）。
谈 seam 时说"适配器"，其他时候说"实现"。

**深度（Depth）**：**接口处的杠杆**。调用方（或测试）每学一单位接口，能驱动多少行为。
大量行为藏在小接口后面 → **深**；接口复杂度几乎等于实现复杂度 → **浅**。

**Seam**（Michael Feathers）：一个"不用改这里就能改变行为"的位置；也就是模块接口**所在的地方**。
**seam 放在哪**是一个独立的设计决策，和"seam 后面放什么"分开决定。
*避免*：boundary（与 DDD 的 bounded context 混淆）。

**适配器（Adapter）**：在某条 seam 上满足某个接口的具体东西。它描述的是**角色**（填哪个槽位），
不是**内容**（里面是什么）。

**杠杆（Leverage）**：调用方从深度里拿到的东西——每学一单位接口换到更多能力。
一份实现，回报给 N 个调用点和 M 个测试。

**局部性（Locality）**：维护者从深度里拿到的东西——改动、bug、知识与验证集中在一处，
而不是摊到各个调用方。修一次，处处修好。

## 深 vs 浅

**深模块** = 小接口 + 大实现：

```text
┌─────────────────────┐
│      小 接 口       │  ← 方法少、参数简单
├─────────────────────┤
│                     │
│      深 实 现       │  ← 复杂逻辑藏在里面
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 小实现（要避免）：

```text
┌─────────────────────────────────┐
│           大  接  口            │  ← 方法多、参数复杂
├─────────────────────────────────┤
│  薄 实 现                       │  ← 只是转手一下
└─────────────────────────────────┘
```

设计接口时逐条问：

- 方法能不能再少？
- 参数能不能再简单？
- 能不能把更多复杂度藏进去？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部完全可以由小的、可 mock、可替换的零件组成，
  它们只是**不出现在接口里**。模块可以同时有**内部 seam**（对实现私有，供它自己的测试用）
  和接口处的**外部 seam**。
- **删除测试（the deletion test）。** 设想把这个模块删掉：复杂度**消失了** → 它本来就是个转手层；
  复杂度**在 N 个调用方那里重新长出来** → 它在挣它那份工资。
- **接口就是测试面。** 调用方和测试穿过同一条 seam。如果你想测到接口**后面**去，
  多半是模块的形状不对。
- **一个适配器只说明 seam 是假想的，两个适配器才说明它是真的。** 除非真有东西在这条 seam 两侧变化，
  否则别引入 seam——单适配器的 seam 只是多一层间接。

## 为可测性而设计

好接口让测试变自然：

1. **接收依赖，不要自己造依赖。**

   ```typescript
   // 可测
   function processOrder(order, paymentGateway) {}

   // 难测
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测
   function calculateDiscount(cart): Discount {}

   // 难测
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面积要小。** 方法越少，要写的测试越少；参数越少，测试的准备工作越简单。

## 词与词的关系

- 一个**模块**恰好有一个**接口**（它面向调用方与测试呈现的那个面）。
- **深度**是**模块**的属性，用它的**接口**来衡量。
- **Seam** 是**模块的接口**所在的位置。
- **适配器**坐在某条 **seam** 上，满足那个**接口**。
- **深度**给调用方产出**杠杆**，给维护者产出**局部性**。

## 被否决的表述

- **把深度定义成"实现行数 / 接口行数"的比值**（Ousterhout）：这会奖励往实现里灌水。
  我们用**深度即杠杆**。
- **把"接口"理解成 TypeScript 的 `interface` 关键字或类的 public 方法**：太窄。
  这里的接口包含调用方必须知道的**每一个事实**。
- **"boundary"**：与 DDD 的 bounded context 重载。说 **seam** 或**接口**。

## 用法（按需要挑一条）

- **只借词汇**：直接用上面的术语表说话，别自己造同义词。
- **深化一簇浅模块**：依赖怎么分类、seam 纪律、测试怎么"替换而不是叠加"，
  见 [references/deepening.md](references/deepening.md)。
- **探索多版接口**：派并行 subagent 把接口设计出几个**根本不同**的版本，
  再按深度、局部性、seam 位置比较，见 [references/design-it-twice.md](references/design-it-twice.md)。

## 反例（不要这样做）

❌ 把术语换成"组件 / 服务 / API / 边界"——词汇一散，这套判据就没用了。
❌ 用实现行数多不多来判"深不深"——深度看的是接口，不是实现体量。
❌ 只把类型签名当接口，不交代不变量、调用顺序、错误模式、性能特征——调用方还是会用错。
❌ 为"将来可能要换"而引入只有一个适配器的 seam——那是间接层，不是 seam。
❌ 把内部 seam 暴露到接口上，只因为自己的测试用得着。
❌ 测到接口后面去测内部状态——实现一改测试就红，说明测试穿错了面。
❌ 深化之后旧的浅模块单测继续留着叠加——该删的没删，维护面反而变大。
❌ 一口气拿第一版接口就开工——重大接口值得先设计两三版再挑（design it twice）。
