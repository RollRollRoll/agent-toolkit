# Code Review — 标准 / 规格双轴审查

## 目标

对 `HEAD` 与用户给定的**固定点**之间的 diff 做**双轴**审查：

- **标准（Standards）**：这段代码守不守本仓库**成文的**编码规范？
- **规格（Spec）**：这段代码有没有**忠实实现**原始 issue / spec？

两轴各跑一个**并行 subagent**，**互不污染对方的上下文**，最后由本 skill 把两份结果聚合起来。

**前置**：issue tracker 应该已经提供给你了。如果 `docs/agents/issue-tracker.md` 不在，
**停下来**让用户先把这份文件补上，不要自己另找一套取 issue 的办法。

**刻意止步于此**：只判这两件事。不改代码、不动 git 状态、不重做设计，
也**不做正确性 / 安全 / 性能那种全面质量审查**——同目录的 `review-changes` 做那件事，
两者可以都跑，但不要互相替代。

> 一句话：**一轴看"写得合不合规矩"，一轴看"做的是不是要的东西"，两轴分开报，谁也别盖住谁。**

## 调用契约

**传入**

- **固定点**：commit SHA、分支名、tag、`main`、`HEAD~5` 等。**没给就问**，不自己挑一个。
- **spec 来源**（可选）：issue 编号或 spec 文件路径；不给就按下文第 2 步自己找。
- **标准来源**（可选）：不给就按下文第 3 步自己找。

**取回**

- `## 标准` 与 `## 规格` 两份报告，**并排呈现**。
- 一行总结：**每轴各自的** findings 数量，以及**每轴内部**最严重的那条。
- spec 找不到时，明确报告"无 spec 可对"，而不是拿标准轴的结论顶上。

**本 skill 不做**

- 不改代码、不 commit、不动 git 状态、不修 findings。
- 不把两轴的 findings 合并或重新排序——**分开报本身就是这套设计的目的**（见文末）。
- 不评审需求或方案本身：有问题作为 finding 报上去。
- 不做五轴质量审查（正确性 / 可读性 / 架构 / 安全 / 性能）。

## 工作流程

### 1. 钉死固定点

用户说的就是固定点。**没说就问**，不要自己猜。

一次性把 diff 命令定下来：`git diff <固定点>...HEAD`（**三点**，比的是 merge-base），
同时用 `git log <固定点>..HEAD --oneline` 记下 commit 清单。

**往下走之前先确认**：`git rev-parse <固定点>` 能解析、diff 非空。
**烂 ref 和空 diff 要死在这里**，不要死在两个并行 subagent 里面。

### 2. 找 spec 来源

按这个顺序找原始 spec：

1. **commit 信息里的 issue 引用**（`#123`、`Closes #45`、GitLab 的 `!67` 等），
   按 `docs/agents/issue-tracker.md` 里的流程取回。
2. **用户作为参数传进来的路径**。
3. `docs/`、`specs/`、`.scratch/` 下**与分支名或特性对得上**的 spec 文件。
4. 都没找到 → **问用户 spec 在哪**。用户说本来就没有 → **规格轴跳过**，
   在最终报告里写明"无 spec 可对"。

### 3. 找标准来源

仓库里任何**成文记录"代码该怎么写"**的东西：`CODING_STANDARDS.md`、`CONTRIBUTING.md`、
`AGENTS.md` / `CLAUDE.md` 里的规范段落等。

在仓库成文的东西之上，标准轴**永远**还要带一份**坏味道基线**——一组固定的 Fowler 代码坏味道
（《重构》第 3 章），**哪怕仓库什么都没写**它也适用。两条规则约束它：

- **仓库覆盖基线。** 成文的仓库标准永远赢；仓库明确认可的写法，即使基线会标它，也压掉不报。
- **基线永远是判断题。** 每条坏味道都是**带标签的启发式**（"疑似 Feature Envy"），
  **不是硬性违规**。和这里所有标准一样：**工具已经能查的，跳过**。

下面 12 条各自读作**是什么 → 怎么修**，拿它去对照 diff。这一整份要**整段贴进标准轴 subagent 的
prompt**——那个 subagent 没有别的途径拿到它。

- **Mysterious Name（名不副实）**：函数、变量或类型的名字**看不出它做什么、装什么**。
  → 改名；**取不出一个诚实的名字，说明设计本身糊**。
- **Duplicated Code（重复代码）**：同一个逻辑形状在这次改动的**多个 hunk 或文件**里出现。
  → 把共同的形状抽出来，两边都调它。
- **Feature Envy（依恋情结）**：一个方法**够到别的对象的数据比够到自己的还多**。
  → 把这个方法**挪到它眼馋的那份数据上**。
- **Data Clumps（数据泥团）**：同样那几个字段或参数**总是结伴出现**（一个想被生出来的类型）。
  → 把它们打包成一个类型，传那个类型。
- **Primitive Obsession（基本类型偏执）**：拿基本类型或字符串**顶替一个该有自己类型的领域概念**。
  → 给这个概念一个自己的小类型。
- **Repeated Switches（重复的分支）**：对同一个类型的同一套 `switch` / `if` 级联
  **在这次改动里反复出现**。→ 换成多态，或者让两处共用同一张映射表。
- **Shotgun Surgery（霰弹式修改）**：**一个逻辑改动**逼你在 diff 里**散着改一堆文件**。
  → 把"总是一起改的东西"收进同一个模块。
- **Divergent Change（发散式变化）**：**一个文件或模块因为好几个互不相干的理由被改**。
  → 拆开，让每个模块**只因为一个理由而改**。
- **Speculative Generality（夸夸其谈通用性）**：为 spec **根本没提的需求**加的抽象、参数或钩子。
  → **删掉**；内联回去，等真实需求出现再说。
- **Message Chains（过长的消息链）**：长长的 `a.b().c().d()` 导航，**调用方本不该依赖这条路径**。
  → 把这段跋涉**藏进第一个对象的一个方法后面**。
- **Middle Man（中间人）**：一个类或函数**几乎只是把调用转手往下传**。
  → 砍掉它，直接调真正的目标。
- **Refused Bequest（拒绝的遗赠）**：子类或实现者**无视或覆盖掉它继承来的大部分东西**。
  → 别继承了，改用组合。

### 4. 并行派出两个 subagent

**标准轴 subagent 的 prompt 要包含**：

- 完整的 diff 命令与 commit 清单；
- 第 3 步找到的标准来源文件清单，**外加整段贴进来的坏味道基线**；
- 简报：
  > 「按文件 / hunk 报告：(a) diff 里每一处违反成文标准的地方——**引用那条标准**（文件 + 规则原文）；
  > (b) 你看到的任何基线坏味道——**点名是哪一条，并引用那段 hunk**。
  > 区分**硬性违规**与**判断题**：成文标准的违反可以是硬性的，基线坏味道**永远是判断题**，
  > 且成文的仓库标准覆盖基线。工具已经能查的跳过。**400 字以内。**」

**规格轴 subagent 的 prompt 要包含**：

- diff 命令与 commit 清单；
- spec 的路径或已取回的内容；
- 简报：
  > 「报告：(a) spec 要求了、但**缺失或只做了一半**的需求；(b) diff 里**没人要求**的行为（范围蔓延）；
  > (c) 看起来实现了、但**实现得不对**的需求。**每条 finding 都要引用对应的 spec 原文行。**
  > **400 字以内。**」

spec 缺失 → **跳过规格轴 subagent**，并在最终报告里写明这件事。

### 5. 聚合

把两份报告放在 `## 标准` 与 `## 规格` 两个标题下呈现，**原文照录或只做轻度清理**。
**不要**合并或重排两轴的 findings——两轴是**刻意分开的**（见文末）。

结尾给**一行**总结：每轴各自的 findings 总数，以及**每轴内部**最严重的那条（若有）。
**不要跨轴评出一个"总冠军"**——那正是这套分离要防的重排。

## 为什么是两轴

一段改动完全可能**过了一轴、挂在另一轴**：

- 每条规范都守了，但**实现的是错的东西** → **标准过，规格挂。**
- 完全照着 issue 做了，但**把项目的约定砸了** → **规格过，标准挂。**

**分开报，才能让一轴盖不住另一轴。**

## 反例（不要这样做）

❌ `docs/agents/issue-tracker.md` 缺失还硬着头皮往下走——该停下来让用户补上它。
❌ 用户没给固定点就自己挑一个（`main`、`HEAD~1`）——固定点定错，整场审查都是错的。
❌ 不先验 `git rev-parse` 和 diff 非空就派 subagent——让烂 ref 死在两个子上下文里。
❌ 用两点 `git diff <固定点>..HEAD` 而不是三点——比错了基准。
❌ 把两轴塞进同一个上下文跑——互相污染，正是并行 subagent 要避免的。
❌ 只告诉 subagent「按坏味道基线看」却不把那 12 条贴进它的 prompt——它根本看不到。
❌ 把基线坏味道当成硬性违规来报，或者拿它去顶掉仓库成文的相反规定。
❌ 报工具（linter / formatter / 类型检查）已经能查出来的东西。
❌ 把两轴 findings 合并成一份"总榜"、跨轴排名、评一个总体结论——分离被你抹掉了。
❌ 找不到 spec 就默默不提，或者拿标准轴的结论冒充"审过了"。
❌ 顺手把 findings 改了——本 skill 只看不改。
