# 测试质量 — 好测试判据、三个反模式、mock 边界

> 用途：`tdd` 闭环里判断"这个测试值不值得写成这样"。红绿循环内没有 reviewer，
> 只能自己认出来。整体审查阶段由 `review-changes` 的测试质量关再核一次。

## 一 · 好测试的五条判据

- **验行为，不验实现**：通过公共接口观察结果。实现可以整体改写，测试不该跟着改。
- **读起来像规格**：`test_empty`（空集合返回 `[]`）一眼看出存在什么能力——描述 WHAT，不是 HOW。
- **期望值来自独立事实来源**：已知字面量、手算样例、spec 里的精确值。
- **能活过重构**：只改结构不改行为时测试仍绿。测试因重构而红，说明它耦合了实现。
- **一个测试一个逻辑断言**：失败时能直接指出坏掉的是哪条行为。

## 二 · 反模式①：实现耦合

**长什么样**：mock 内部协作者、测私有方法、断言调用次数 / 顺序、绕过被测接口从侧信道验证
（调用 `createUser` 后直接查库断言那行存在）。

**识别信号**：只改结构、没改行为，测试红了。

**怎么改**：从**同一个接口**读回来验——`createUser` 之后用 `getUser` 取，断言取到的内容。
测试只认识 seam，不认识 seam 后面的分工。

## 三 · 反模式②：同义反复

**长什么样**：期望值按代码的同一套算法重算一遍。

```text
expect(calculateTotal(items)).toBe(items.reduce((a, i) => a + i.price, 0))   ❌
expect(calculateTotal(items)).toBe(15)                                       ✅
```

按同样方式手推出来的快照、常量断言等于它自己，都属于同一类。

**识别信号**：把实现改成任意等价写法，测试永远绿；把实现改错，测试**也**跟着一起错——
它按构造必然通过，永远不可能与代码不一致。

**怎么改**：换成独立字面量、手算样例，或 spec 里写死的精确值。

## 四 · 反模式③：水平切片

**长什么样**：先把所有测试写完，再去写所有实现。

**识别信号**：一次提交里出现一批从没红过的测试；测试覆盖的是模块结构的形状，
而不是用户可见行为。

**怎么改**：走**垂直切片**——一个测试 → 一个最小实现 → 下一个。每个测试都是 **tracer bullet**，
回应上一轮学到的东西。

## 五 · mock 边界

- **可以 mock**：外部 API、第三方服务、时间与随机源，（有时）数据库与文件系统。
- **不要 mock**：自己的模块、内部协作者、被测单元的下游实现。
- 判据：mock 的是**系统边界之外**的东西吗？是自己写的代码就别 mock——
  mock 掉它等于把测试钉死在当前分工上。

## 六 · 难测的地方怎么办

测不动通常不是测试的问题，是设计的问题：行为被埋在 IO / 框架 / 网络外壳里。
**把行为挤到 seam 内侧，外壳留薄**——纯函数拿数据算结果，外壳只负责搬运。
外壳薄到一眼看完就不必硬测。

若挤不动、且改结构会越界（超出当前改动范围）→ 写进「疑虑」交回调用方，不在红绿之间顺手重构。
