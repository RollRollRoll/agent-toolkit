# 模型选择 — 阶段 3 派发 subagent 时按角色定档

> 用途：阶段 3 派发整体验收 review / fix 时，据此选模型档位。
> **阶段 2 没有定档动作**：任务由主 agent 自己执行（调用 `tdd` 是加载纪律、不是派发），
> 用的就是当前 session 的档位。
> 目标：用够用的最省档位控成本、提速度；但**轮次数比单价更影响总成本**——档位选错反而更贵。

## 一 · 铁律

- **派发时必须显式指定模型**——不写等于让 subagent 继承主 agent 当前档位（通常是最贵最强档），
  悄悄废掉分档的意义。
- 三档：**cheap（便宜档）/ standard（标准档）/ most-capable（最强档）**——具体对应平台上哪个模型，
  由当前平台与账号实际可用模型决定，不在此写死。平台参数映射见 [platform-agents.md](platform-agents.md)。

## 二 · 按角色定档

| 派发对象 | 默认档位依据 | 升档信号 |
|---|---|---|
| 阶段 3 整体验收（派 subagent 加载 `review-changes`） | 固定 **most-capable**——不用 session 默认档位，这是全链路唯一的架构级判断点，也是唯一一次 subagent 派发 | — |
| 阶段 3 fix subagent | 与整体验收发现的复杂度匹配，通常 **standard**；涉及并发 / 状态机 / 安全边界 → **most-capable** | 复审仍不过、问题涉及原设计 → 停下退回上游，不是无限升档硬修 |

**cheap 档在本 skill 里没有位置**：只剩下的两个派发点，一个是唯一的架构判断门，一个是修它审出来的
Critical / Important——两者都不是"照抄转录"型工作。

## 三 · 阶段 2 的档位问题在别处

任务内不派 subagent，所以没有"给执行方定档"这件事。但同一个成本权衡换了个形式存在：
主 agent 自己走 `tdd` 的闭环、任务内没人复核，**session 档位太低的代价不是"多修一轮"，
而是"缺陷带着一堆绿测试进 commit"**，等到阶段 3 才被审出来时返工范围已经是整条分支。
判断 session 档位是否够用，看的是同一件事——不够就停下来告诉用户，而不是硬着头皮往下写。

## 四 · 轮次数比单价更重要

- 便宜档在多步任务上经常要 2~3 倍轮次，折算下来不一定省。
- 更贵的是**看不见的返工**：写出同义反复测试或测在实现细节上，测试全绿、闸门一也过得去，
  等到阶段 3 才被审出来，返工范围已经是整条分支。

## 派发前自查

- 阶段 3 每次派发都**显式指定了模型与必要的推理档位**（Claude Code 用 Agent `model`；
  Codex 用 agent 配置或派发时支持的 model / reasoning 参数），没有留空任其继承主 agent？
- 整体验收固定用了 most-capable，没有沿用 session 默认档位？
- 没有在阶段 2 派 subagent（那里本就不该有派发，也就不该有定档）？
