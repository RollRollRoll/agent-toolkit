# 验收与收尾 — 双验收门、整体审查编排、覆盖回扫、分工边界、收尾

> 用途：`execute` 招牌机制「双验收闸门」+ 阶段 3/4 的操作细则。
>
> **两道门**：每任务证据门（闸门一，阶段 2 内，只核 TDD 证据与验证结果）+ 整体验收门（闸门二，阶段 3，
> 唯一的审查与修复轮）。
>
> **审查判据不在这里**：五轴 + 测试质量的逐关判据住在 `review-changes`
> （`references/axes.md`）。本文件只管**怎么编排这道门**：什么时候派、传什么、拿回来怎么处理。

## 一 · 每任务验收门（闸门一：证据门，不是审查门）

任务由**主 agent 自己**执行（调用 `tdd` 走闭环），任务内**不派任何 subagent，也没有独立审查轮与修复轮**——
质量由红 → 绿 TDD 本身承担，闸门一只核**可机械判定的证据**：

- **验收标准逐条对上**任务清单给的那份，不多不少。
- **红 → 绿证据齐**：tdd 交回的执行记录里每个行为都有实现前的失败输出（含"为何预期失败"）+
  实现后的通过输出，且是当场写的。只有绿没有红 → **交回 tdd 把那个行为重做一遍红 → 绿**；
  做不到就记录并告知用户，别拿事后补的测试冒充红证据。
- **验证方式收尾实跑绿**：提交前完整跑一次任务的验证命令（加 typecheck / 相关测试），输出里的告警也要看见。
- **范围没漂**：HEAD 仍是 `task-baseline.sh` 记录的基线，改动落在任务涉及文件内。
- **不齐不 commit、不标 `[x]`**：三样证据缺任何一样都不许进账本。齐了先标 `[x]`，与代码 / 测试一起提交；
  提交成功后才写 ignored ledger。
- 这是任务级"做完没做完"的客观判据，不靠"看起来写好了"，也不靠再派一个 agent 说"看过了"。
  判据是**落盘的输出**，不是"我记得都跑绿了"。
- tdd 交回的结构疑虑记进账本，**留给闸门二的 architecture 关**，不在任务内开审查轮。

## 二 · 整体验收门（闸门二）：调用 review-changes

**输入准备**：先检查本次开发 diff 中的临时日志、调试打印、断点和临时开关；有残留就精准清理、
跑覆盖测试，并在阶段 0 授权范围内提交。确认真实工作区干净后再派发——`review-changes` 的
`scripts/review-package.sh` 会拒绝任何非忽略 dirty 状态，让 reviewer 审一个漏掉未提交改动的包等于没审。

全部任务完成后，主 agent **派独立 subagent 加载 `review-changes`** 对整条分支做审查——
这是整个 execute **唯一**的 subagent 派发点，fresh 上下文正是它的价值：
写代码的是主 agent 自己，审的必须是没参与过实现的那一个。
**这次派发固定用 most-capable（最强档）模型，不沿用 session 默认**——任务级只有证据门、没有审查轮，
这里是全链路唯一的架构级判断点，判据见 [model-selection.md](model-selection.md)。

**传给它**（照 [handoff-templates.md](handoff-templates.md) 第二节模板填空）：

- **BASE 起点 commit**（阶段 0 记入账本的那个）——它自己跑 `review-package.sh` 生成审查包。
- **需求依据**：tasks 文件、design / spec 路径。
- **执行期疑虑**：各任务 tdd 交回、记在 ledger 里的结构问题——architecture 关优先看这些点。

**拿回来**：带 `file:line` 的 Critical / Important / Minor findings + 六关判定。
Critical / Important **派独立 fix subagent** 修复 → 复审（**按轮次计，默认 3 轮**；
超限仍有 Critical / Important 就停下交用户判断），Minor 记录不阻塞。

**fix 循环（commit-then-review）**：fix subagent 修完后，主 agent **先 commit 再复审**——
让 reviewer 重新生成一份新包（轮次递增，HEAD 已前进，新包已含 fix），复审读新包，不复用旧包。
与任务级"证据不齐不 commit"**有意不同**：任务级的 commit 是闸门记号；阶段 3 面对的本来就是已 commit 的分支，
闸门记号是"整体验收通过"状态本身，fix commit 只是普通代码演进。
涉及行为的修复仍**先补失败测试再修到绿**，报告里留红 → 绿证据。
这些 fix commit 也必须落在阶段 0 的明确批次授权内；超出授权范围就重新确认。

## 三 · 覆盖核对回扫（本 skill 自己做，review-changes 不做）

对回上游，确认没落空（这是这条链"可验证"基因在执行末端的收口）。它需要上游产物与任务清单，
是本 skill 自己的活：

- 对回任务清单的**覆盖核对表**：design 每个组件 / Decision、spec 每条 Requirement / MUST NOT →
  都**已实现**、且**被测试或检查覆盖**了吗？
- 对回 spec 的**成功标准**：每条都能跑通验证了吗？
- 有落空（某设计点没实现 / 没测试）→ 回阶段 2 补任务，别让它溜过整体验收。

## 四 · 上游纠错与分工边界

执行中发现 design / spec / tasks 有误，分级处理：

- **小问题**（笔误、明显小遗漏、不动结构）→ 就地修正 + 回写 artifact + 告知用户，继续。
- **重大问题**（技术决策错、需求缺、任务依赖不存在的设计）→ 停下退回 plan / task，
  不在执行里硬改。
- 检验：「这修正会改变已 review 的行为契约 / 技术决策 / 任务边界吗？」会 → 重大，退回上游。

## 五 · 收尾（调用 finish-branch）

- **整体验收通过后，调用 `finish-branch` 做收尾**：它会先清理本次开发的调试残留并重跑最终测试，再检测
  repo/worktree 状态，给出合并到主干 / 本地保留 / 创建 PR / 丢弃选项。
- **危险操作 gate**：commit 必须已有阶段 0 明确授权；合并 / PR / push / 丢弃 / 移除 worktree **不自动做**，
  由 finish-branch 对具体动作逐项取得用户确认（遵循当前 `CLAUDE.md` / `AGENTS.md` 与平台审批策略）。
- execute 到"整体验收通过 + 收尾决策交付"为止，不擅自合并、不自动往下。

## 收尾自检

- 每任务都过了闸门一的三样证据（红 → 绿齐、收尾完整跑一次验证命令绿、HEAD 未漂移）才 commit / 标 `[x]`？
  任务内一个 subagent 都没派，也没有拿"事后补的测试"当红证据？
- 整体验收**派独立 subagent 加载了 review-changes**，且**固定用了 most-capable 档位**？
  传了 BASE、需求依据和各任务疑虑？
- 派发前确认了工作区无非忽略改动（否则它的 `review-package.sh` 会拒绝生成包）？
- 审出的 Critical / Important 派独立 fix subagent 修了？fix loop 按轮次计、超限停下交用户？
  fix 后复审用的是 commit 过再重新生成的新包？
- 整体验收包生成前清掉了本次开发的调试残留，并在清理改动后重新跑了覆盖测试？阶段 3 fix commit 仍在用户授权内？
- **覆盖核对回扫自己做了**——design / spec 每条都实现且被测试覆盖、不落空？
- 全套测试 / 构建 / typecheck 绿？
- 发现上游错误按"小修就地 / 重大退回"处理了？
- 收尾**调用了 finish-branch**、交用户拍板，没擅自合并 / PR / push？
