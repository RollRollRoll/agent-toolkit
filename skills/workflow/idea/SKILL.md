# Idea — 概念确认（第 1 棒）

## 你的任务

把一个**还没想透的想法**推进到**一个被用户显式确认过的概念**，作为整条开发链的起点。

你不亲手定义怎么挖意图、怎么问边界——那交给被调用的 skill；你钉死的是**编排层的三件事**：

1. **把想法交给对的能力** —— 调用 **refine-idea** 产出概念（六行复述 + 被剪分支 + 挂起项）。
2. **守确认门禁** —— 拿到**显式确认**才算过门；模糊回应不算。
3. **止步于概念** —— 过门后交还用户，不自动往下写 spec、不碰技术、不写代码。

> 一句话：调 refine-idea 把"我想要个 X"打磨成"我们要解决 Y、做 A/B、不做 C/D、成功标志 Z"，
> 再让用户当面认下来。

## 能力调用

本 skill 是 `idea → plan → task → execute` 这条开发链的第 1 棒。链上每一棒各守一道闸门、
把产物交给下一棒。概念打磨的**具体能力**交给下面这个 skill：

| 调用点 | skill | 传入 | 取回 |
|---|---|---|---|
| 阶段 1 打磨概念 | **refine-idea** | 原始想法（越原样越好）、已知约束、是否落盘 | 六行概念复述、被剪掉的分支、挂起项、落盘路径 |

两条调用约定：

- **调用即交出判据定义权**：不在本 skill 里重述 refine-idea 的 Q+GUESS 与 grilling 规则——
  需要细节时读那个 skill，别在这里维护第二份。
- **被调 skill 不可用时，闸门判据不变**：主 agent 按同一套要求自己走一遍（挖意图 → 问穷尽边界 →
  六行复述），并说明降级原因——**降级的是谁来做，不是做不做**。

## 何时用 / 何时不用

**适用**：用户抛来一个宽泛、模糊、还没想透的想法；或需求里夹带"scalable / 干净的架构 /
业界标准做法"这类"听上去应该想要"的词；或用户自己就说"还没想清楚 / 帮我理一理"。

**不适用**（别硬套）：

- 需求已经足够明确、边界自包含 → 直接进 **plan**。
- 要的是技术选型 / 架构 / 实现方案 → 那是 **plan**。
- 单行修复、错别字这类小改动。
- 已在写代码、定位 bug、做评审。

**⚠️ 加载约束（硬性）**：本 skill 需要一个**能实时响应的活人**在对话另一头。
**禁止在 CI、定时任务、自治循环等非交互场景中调用**。在那种场景里遇到模糊需求，正确做法是
**把它标记为 blocker 并停下**，而不是替用户臆测意图往下跑。

## 工作流程

### 阶段 0 · 定位

1. **判是不是这一棒**：想法已经边界清晰的，直接说"这个可以进 plan 了"，别硬走一遍。
2. **判规模**：如果这其实是多个独立子系统（"一个带聊天、计费、分析的平台"），
   **先提示拆分**，拆出独立的小块逐个走本链。
3. **探上下文**：若在一个代码库里运行，先探索现有结构，让边界讨论落在真实约束上。

### 阶段 1 · 调用 refine-idea

按其调用契约传入：原始想法、已知约束、是否落盘（默认不落盘）。

取回：六行概念复述（要解决什么 / 给谁 / 为什么是现在 / 成功长什么样 / 硬约束 /
**明确不做什么**）、被剪掉的分支、挂起项。

- 交回 **BLOCKED**（问了几轮置信度仍不涨）→ **停下把判断告诉用户**，别在原地死磕。
- 复述里"明确不做什么"为空 → 交回补，这一项不能空。

### 阶段 2 · 用户确认门禁

1. 把六行复述**连同被剪掉的分支与挂起项**一起摆给用户——别让他以为整棵树都问过了。
2. 请用户确认，并明确这条规矩：
   > **未经确认的概念，不进入 spec / 技术方案。**
3. 用户要改 → 回阶段 1 让 refine-idea 重新打磨对应那一层，再重新确认。
4. 拿到**显式确认** → 过门。

**哪些回答不算 "yes"**：

- "你看着办 / 都行" = 委托，不是决策。
- "听起来不错" = 模糊回应，不是收敛。
- 沉默后一句"那就开始吧" = 放弃，不是同意。

### 阶段 3 · 交接

- 把确认过的概念交还用户。可以一句话提示"需要的话，可据此进入 **plan**（写 spec + 定技术方案）"，
  但**不自动调用下游、不写 spec、不写代码**。本 skill 到"概念确认"为止。
- 用户要留档时，落盘由 refine-idea 完成（默认 `docs/proposal/<名字>.md`）；
  目录不存在**先问用户**再建，不要默默 `mkdir`。

## 产物与交接

- **默认不落盘**：概念在对话里确认即可；要留档才写 `docs/proposal/<名字>.md`。
- 概念**绝不含**技术选型、架构、任务拆解——那些留给下游。
- 交给下一棒（plan）的是：确认过的六行概念 +（若有）概念单路径 + 挂起项。

## 反例（不要这样做）

❌ 用户说"做个 dashboard"，直接接住开始定 dashboard 的功能 —— 没让 refine-idea 挖真正的痛点。
❌ 在本 skill 里重述一遍 refine-idea 的 Q+GUESS 或 grilling 规则 —— 判据该住在被调 skill 里。
❌ refine-idea 交回的被剪分支与挂起项不摆给用户，让他以为整棵树都问过了。
❌ 用户回一句"你看着办"，就当作确认通过。
❌ 复述里"明确不做什么"是空的，仍然过门。
❌ 概念还没确认，就开始写 spec / 拆任务 / 敲代码。
❌ 过门后自动调用 plan —— 本 skill 到概念确认为止，往下走是用户的决定。
❌ 把"用 SQLite 存储 / React 前端"放进概念 —— 越界到技术实现层。
❌ 想法本来就边界清晰，还硬走一遍这一棒 —— 直接进 plan。
❌ 在 CI、定时任务、自治循环里调用本 skill，遇到模糊需求自己脑补意图往下跑。
