# Task — 任务拆解（第 3 棒）

## 目标

把一份**已确认的技术设计**推进到**一份被用户确认过的开发任务清单**，每个任务都能独立验收。

你不亲手定义怎么切片、怎么定序——那交给被调用的 skill；你钉死的是**编排层的三件事**：

1. **把设计交给对的能力** —— 调用 **split-task** 产出任务清单（任务条目 + 依赖与并行视图 + 覆盖核对表）。
2. **守确认门禁** —— 核一遍覆盖不落空、不镀金，再拿**显式确认**才算过门。
3. **止步于清单** —— 过门后交还用户，不自动开始编码、不自动跑任务。

> 一句话：调 split-task 把技术设计拆成"可独立验收、依赖理顺、对得上 design 与 spec"的任务清单，
> 再让用户当面认下来。

## 能力调用

本 skill 是 `idea → plan → task → execute` 这条开发链的第 3 棒。链上每一棒各守一道闸门、
把产物交给下一棒。任务拆解的**具体能力**交给下面这个 skill：

| 调用点 | skill | 传入 | 取回 |
|---|---|---|---|
| 阶段 1 拆任务 | **split-task** | 已确认的 design 路径、spec 路径（取验收口径）、落盘位置、切片偏好与优先级、范围提示 | tasks 路径、自检结论、需拍板的点、推断假设、待解问题 |

两条调用约定：

- **调用即交出判据定义权**：不在本 skill 里重述 split-task 的垂直切片与拆分探针规则——
  需要细节时读那个 skill，别在这里维护第二份。
- **被调 skill 不可用时，闸门判据不变**：主 agent 按同一套要求自己走一遍（垂直切片 → 探针补漏 →
  定序 → 覆盖核对），并说明降级原因——**降级的是谁来做，不是做不做**。

## 何时用 / 何时不用

**适用**：技术设计已确认（理想是 plan 确认过的），准备进入编码前，要把一个功能 / 改动落地为
"可被领取、可逐个验收、可勾选追踪"的任务。

**不适用**（别硬套）：

- 技术方案还没定 / 没确认 → 先 **plan**。任务必须站在确认过的技术设计上。
- 想法还模糊 → 先 **idea**。
- 要动手写实现 → 那是 **execute**。
- 已在写代码、定位 bug、做评审。

**⚠️ 加载约束**：本 skill 的产出**最终必须经一个能 review 的活人确认才放行进入编码**。
允许从 design + spec + 代码库推断常规拆分（显式标注假设），但**会改变清单形状 / 需用户偏好**
的点（切片边界、任务粒度、关键依赖顺序、哪些延后到后续版本）必须停下来交用户拍板。
禁止在 CI / 定时任务 / 自治循环里把它当"自动产任务、无人 review 就开干"的工具——那种场景遇到
"没有任务清单"，正确做法是产出**带假设标注的草案并标记为待 review 的 blocker**。

## 工作流程

### 阶段 0 · 定位

1. **接上游**：读 design（`docs/design/*` 或用户指明位置）作为主输入，读 spec（`docs/specs/*`）取验收口径。
   **无 design / design 没确认** → **建议先 plan**，不要自己去补技术决策。
2. **判规模**：若这其实是多个独立子系统，**先提示拆分**，逐个出任务清单，
   别把一份清单撑成全系统施工总表。

### 阶段 1 · 调用 split-task

按其调用契约传入：已确认的 design 路径、spec 路径、落盘位置（缺省跟随仓库约定）、
切片偏好与优先级（有就给，省得它来问）、范围提示（greenfield / brownfield delta）。

取回：tasks 路径、自检结论、**需拍板的点**、推断假设、待解问题。

- 交回 **BLOCKED**（design 有缺口，要拆的任务依赖一段不存在的设计）→ **停下退回 plan** 补设计，
  重走它的确认，再回来。别用任务清单去替设计补决策。
- 有"需拍板的点"（切片边界 / 粒度 / 关键顺序 / 哪些延后）→ 连同推荐一起摆给用户，
  拿到答复后交回 split-task 收进清单。

### 阶段 2 · 用户确认门禁

1. **自己核一遍**：
   - design 每个组件 / Decision、spec 每条 Requirement / MUST NOT 在**覆盖核对表**里都有任务落点（不落空）。
   - 没有 design / spec 之外的镀金任务。
   - 依赖**无环**、顺序可执行；判定为"需任务"的迁移 / 兼容 / 回滚都写成了完整 `Task N`，
     不是游离 bullet（否则 execute 抽不出来）。

   缺了 → 交回 split-task 补。
2. 把 tasks 路径 + 自检结论 + 推断假设 + 待解问题摆给用户，请他 review，并明确这条规矩：
   > **未通过 review 的任务清单，不进入编码。**
3. 用户要改 → 回阶段 1 修订并重过自检，再重新确认。
4. 拿到**显式确认** → 过门。

**哪些回答不算 "yes"**：

- "你看着办 / 都行" = 委托，不是决策。
- "听起来不错" = 模糊回应。
- 沉默后一句"那就开始吧" = 放弃，不是确认。

### 阶段 3 · 交接

可以一句话提示"需要的话，可据此进入 **execute**（逐个任务执行）"，
但**不自动开始编码、不自动跑任务**。本 skill 到"任务清单确认"为止。

## 产物与交接

- **单份任务清单文档**，位置跟随仓库既有约定——已有 OpenSpec 式 `openspec/changes/<change>/tasks.md`
  或 `docs/tasks/` 就跟随；否则缺省 `docs/tasks/<YYYY-MM-DD>-<主题>-tasks.md`（目录不存在先确认）。
- **brownfield** 用 delta，只列改动相关任务 + 迁移 / 兼容 / 回滚。
- 交给下一棒（execute）的是：确认过的 tasks 路径 + design / spec 路径（取验收口径）+ 待解问题。

## 反例（不要这样做）

❌ design 还没过门就开始拆任务 —— 给没定的方案拆活，该先 plan。
❌ 在本 skill 里重述 split-task 的垂直切片或拆分探针规则 —— 维护两份必然漂移。
❌ split-task 回 BLOCKED 说 design 有缺口，却在任务里顺手把技术决策定了 —— 该退回 plan。
❌ 交回后不核覆盖，design 某个组件或 spec 某条 MUST 没人做也照样过门。
❌ 反过来，放行了一堆 design / spec 之外的"顺手加的"任务（镀金）。
❌ 依赖有环 / 顺序排错也过门，或迁移 / 回滚只留游离 bullet 没写成 `Task N` —— 下游抽不出来。
❌ 切片边界 / 粒度 / 关键顺序自己替用户拍板就过门。
❌ 用户回一句"你看着办"，就当作确认通过。
❌ 过门后自动调用 execute 或开始写代码 —— 往下走是用户的决定。
❌ 接 issue tracker / 外部平台发任务 —— 本链是本地文档驱动，不做外部集成。
❌ 在 CI / 自治循环里自动产任务清单、无人 review 就开干。
