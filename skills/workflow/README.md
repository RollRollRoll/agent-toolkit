# skills/workflow/

## 这个目录装什么

**开发链的四棒编排器**：`idea → plan → task → execute`。

判断标准（三条同时满足才放这里）：

1. **它是链上的一棒**：在 `idea → plan → task → execute` 这条固定顺序里占一个位置，
   上一棒的产物是它的输入，它的产物是下一棒的输入。
2. **它只做编排、闸门与用户确认**，具体能力交给 `../development/` 下的 composable skill；
   **自己不定义能力判据**，需要细节就去读被调 skill。
3. **它是门禁的归属方**：被调 skill 只产内容，"过没过、要不要往下"由这一棒判定；过门后不自动往下。

反过来说：**只要它自己写判据、或者可以被别人当能力单元调用，它就不属于这里**——那是 `../development/`。

## 当前成员

| skill | 位置 | 职责 |
|---|---|---|
| `idea` | 第一棒 | 把宽泛模糊的想法打磨成边界清晰、可执行的概念并拿到确认 |
| `plan` | 第二棒 | 依次产出行为规格与技术设计，各守一道确认门禁 |
| `task` | 第三棒 | 把已确认的技术设计拆成开发任务清单并拿到确认 |
| `execute` | 第四棒 | 把任务清单逐个落地成实现、测试与提交，并经验收确认真的做完 |

各棒调用哪些 composable skill、传入取回什么，见仓库根 `README.md` 的调用点表格。

## 和架构分层的关系

这个目录**恰好等于** workflow 层——架构层次没有单独的声明文件，
`skills/workflow/` 下这四个就是 workflow 层的全部。这是三个场景目录里唯一"目录 = 分层"的一个；
`development/` 和 `support/` 里的 skill 是不是 composable 能力单元，得看它 `SKILL.md` 里
有没有「调用契约」章节。

## 新增时

这条链的形状是稳定的，正常不会加第五棒。真要加，先确认它不是"某一棒内部的一个能力"——
那种应该进 `../development/` 并写清调用契约，由对应的棒来调。
