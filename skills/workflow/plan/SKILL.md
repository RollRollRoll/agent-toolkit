# Plan — 规格与技术方案（workflow 层 · 第 2 棒）

## 你的任务

把一个**边界已清晰的概念**推进到**两份被用户确认过的文档**：一份**行为规格（spec）**说清
"做成什么样、怎么验收"，一份**技术设计（design）**说清"怎么实现、为什么这么定"。

你不亲手定义怎么写 Scenario、怎么比较方案——那交给 composable 层；你钉死的是**编排层的四件事**：

1. **先行为、后技术** —— 先调 write-spec 把行为契约钉死，确认后才调 make-design 做技术决策。
   技术方案必须站在确认过的行为契约上。
2. **两道确认门禁** —— spec 一道、design 一道，各自拿到**显式确认**才往下。
3. **对得上号** —— design 交回时核一遍：spec 每条 Requirement / MUST NOT 都有设计落点，不落空、不镀金。
4. **止步于方案** —— 过门后交还用户，不自动拆任务、不写代码。

> 一句话：调 write-spec 把"系统 MUST 这样、MUST NOT 那样"钉死并确认，再调 make-design
> 把它翻译成一套有据可查的技术决策并确认。

## 分层与调用

本 skill 是 **workflow 层**第 2 棒。workflow 层是 `idea → plan → task → execute` 这条链，
各守一道闸门、把产物交给下一棒。规格与设计的**具体能力**交给 composable 层：

| 调用点 | composable skill | 传入 | 取回 |
|---|---|---|---|
| 阶段 1 写行为规格 | **write-spec** | 需求依据（概念 / 概念单路径）、落盘位置、调研决策、范围提示 | spec 路径、自检结论、待解问题 |
| 阶段 3 定技术方案 | **make-design** | 已确认的 spec 路径、落盘位置、已知约束与偏好、范围提示 | design 路径、自检结论、需拍板的点、推断假设、待解问题 |

三条跨层约定：

- **调用即交出判据定义权**：不在本 skill 里重述 write-spec 的双探针、也不重述 make-design 的
  决策探针与方案对比规则——需要细节时读那个 skill，别在这里维护第二份。
- **顺序不可换**：design 的输入是**已确认的** spec。spec 没过门就调 make-design，等于给没定的需求做方案。
- **被调 skill 不可用时，闸门判据不变**：主 agent 按同一套要求自己走一遍，并说明降级原因——
  **降级的是谁来做，不是做不做**。

## 何时用 / 何时不用

**适用**：概念已清楚（理想是 idea 确认过的），准备进入实现前，需要一份实现期可对照的行为规格，
以及一套会牵动后续大量工作的技术决策（选型 / 架构 / 数据模型 / 接口契约）。

**不适用**（别硬套）：

- 想法还模糊、意图不明确 → 先 **idea**。
- 要的是任务拆解 / 实现计划 / 排期 → 那是 **task**。
- 要动手写实现 → 那是 **execute**。
- 单行修复、错别字，或范围完全自包含的小改动。
- 已在写代码、定位 bug、做评审。

**⚠️ 加载约束**：本 skill 的产出**最终必须经一个能 review 的活人确认才放行进入实现**。
其中 spec 段是硬性交互——禁止在 CI / 定时任务 / 自治循环里把它当"自动产 spec"的工具；
design 段允许推断常规决策（显式标注假设），但**重大且难逆 / 需用户偏好与约束**的决策
必须停下来交用户拍板。非交互场景遇到"没有 spec / 没有方案"，正确做法是
**产出带假设标注的草案并标记为待 review 的 blocker**，而不是自动定稿往下冲。

## 工作流程

### 阶段 0 · 定位

1. **接上游**：读概念（`docs/proposal/*` 或用户指明位置 / 对话里已确认的概念）。
   **概念还没清**（连"要解决什么"都说不清）→ **建议先 idea**，不要自己臆测意图。
2. **判起点**：手上已有确认过的 spec → 跳过阶段 1、2，直接从阶段 3 起。
3. **判规模**：若这其实是多个独立能力 / 子系统，**先提示拆分**，逐个走本棒，
   别把一份 spec 撑成全系统说明书、一份 design 撑成全系统架构书。

### 阶段 1 · 调用 write-spec

按其调用契约传入：需求依据、落盘位置（缺省跟随仓库约定）、**功能空间调研决策**
（greenfield 时你要么已从用户处拿到，要么让 write-spec 去问）、范围提示（greenfield / brownfield delta）。

取回：spec 路径、自检结论、待解问题。交回 **BLOCKED**（概念没清）→ 停下告诉用户，建议回 idea。

### 阶段 2 · spec 确认门禁

1. 把 spec 路径 + 自检结论 + 待解问题摆给用户，请他 review，并明确这条规矩：
   > **未通过 review 的 spec，不得采用，也不进入技术方案。**
2. 用户要改 → 回阶段 1 让 write-spec 修订并重过自检，再重新确认。
3. 拿到**显式确认** → 过门，进阶段 3。

### 阶段 3 · 调用 make-design

按其调用契约传入：**已确认的** spec 路径、落盘位置、已知约束与偏好（技术栈限制、不可引入的依赖、
性能预算、兼容与安全边界）、范围提示。

取回：design 路径、自检结论、**需拍板的点**、推断假设、待解问题。

- 交回 **BLOCKED**（spec 有缺口，某个决策依赖一段缺失的行为契约）→ **退回阶段 1**
  让 write-spec 补这段行为，重走阶段 2 的确认，再回来。别用技术方案去替 spec 补行为。
- 有"需拍板的点"→ 连同推荐一起摆给用户，拿到答复后交回 make-design 收进 design。

### 阶段 4 · design 确认门禁

1. **自己核一遍覆盖**：spec 每条 Requirement / MUST NOT 在 design 的「需求覆盖核对」里都有落点
   （不落空），且没有 spec 之外的镀金。缺了 → 交回 make-design 补。
2. 把 design 路径 + 自检结论 + 推断假设 + 待解问题摆给用户，请他 review，并明确这条规矩：
   > **未通过 review 的技术方案，不进入任务拆解 / 编码。**
3. 用户要改 → 回阶段 3 修订并重过自检，再重新确认。
4. 拿到**显式确认** → 过门。

**哪些回答不算 "yes"**（两道门禁通用）：

- "你看着办 / 都行" = 委托，不是决策。
- "听起来不错" = 模糊回应。
- 沉默后一句"那就开始吧" = 放弃，不是确认。

### 阶段 5 · 交接

可以一句话提示"需要的话，可据此进入 **task**（任务拆解）"，但**不自动调用下游、不开始写代码**。
本 skill 到"spec 与技术方案都确认"为止。

## 产物与交接

- **两份文档**，位置跟随仓库既有约定：spec 缺省 `docs/specs/<YYYY-MM-DD>-<主题>-spec.md`，
  design 缺省 `docs/design/<YYYY-MM-DD>-<主题>-design.md`（目录不存在先跟用户确认）。
- **brownfield** 两份都用 delta：spec 只写 ADDED / MODIFIED / REMOVED，
  design 聚焦改动 + 对现有系统的影响与迁移，不重述整套既有架构。
- 交给下一棒（task）的是：确认过的 design 路径 + spec 路径（取验收口径）+ 两份的待解问题。

## 反例（不要这样做）

❌ spec 还没过门就调 make-design —— 给没定的需求做方案。
❌ 把两道门禁合成一道，spec 和 design 一起丢给用户"看一下" —— spec 错了会带着 design 一起返工。
❌ 在本 skill 里重述 write-spec 的双探针或 make-design 的方案对比规则 —— 维护两份必然漂移。
❌ make-design 回 BLOCKED 说 spec 有缺口，却在方案里顺手把行为补了 —— 该退回阶段 1。
❌ design 交回后不核覆盖，spec 某条 MUST 没有设计落点也照样过门。
❌ 反过来，放行了一堆 spec 之外的"顺手加的"设计（镀金）。
❌ 重大且难逆、或需用户偏好的技术决策，自己替用户拍板就过门。
❌ 用户回一句"你看着办"，就当作确认通过。
❌ 过门后自动调用 task 或开始写代码 —— 往下走是用户的决定。
❌ 概念其实还没想清，却硬起 plan —— 该先 idea。
❌ 在 CI / 自治循环里自动产 spec / 方案、无人 review 就往下跑。
