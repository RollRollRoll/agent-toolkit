# Write Spec — 行为规格 Skill

## 你的任务

把一个**边界已经清晰的想法 / 需求**，转化为一份**可被验证的行为规格**：

1. **系统该有什么可观察行为** —— 用 Requirement + MUST 表达，每条都配 Scenario（WHEN→THEN）。
2. **明确必须不发生什么** —— 把"不做什么"转成 MUST NOT 负向需求 + 可验证检查。
3. **边界场景下如何表现** —— 边界值 / 空值 / 并发 / 幂等…… 逐项比对，适用的写成 Scenario。
4. **怎么算做完了** —— 可执行的成功标准，不是"能用就行"。

spec 是**编码前的最后一道闸门**。需求里每一处没说清的行为、每一个没被表态的边界、每一条沉默的
"不做什么"，都会在实现期变成返工、扯皮或上线事故。写成可被验证的契约，让"做完没做完"不再靠口头判断。

**刻意止步于此**：不挖意图、不做技术选型、不画架构、不拆任务、不排期。
你的产出是一份"行为说清楚了、验收定死了、可以放心进入实现"的规格，而不是实现方案。

> 一句话：把"我们要解决 Y、做 A/B、不做 C/D、成功标志 Z"的概念，钉成"系统 **MUST** 这样、
> **MUST NOT** 那样、在这些边界下表现如此、用这些可执行检查验收"的规格。

## 何时用 / 何时不用

**适用**：概念已清楚、准备进入实现前，需要一份实现期可对照、验收时可逐条核对的可验证规格
（新增能力，或改既有功能）。

**不适用**（别硬套）：

- 概念还模糊、意图不明确 → 先 refine-idea。
- 要的是技术选型 / 架构 → 那是 make-design。
- 单行修复、错别字，或需求已非常明确、范围完全自包含的小改动。
- 已在写代码、定位 bug、做评审。

**⚠️ 加载约束（硬性）**：本 skill 的产出必须经一个**能实时 review 的活人**确认才放行。
禁止在 CI / 定时任务 / 自治循环等非交互场景里把它当作"自动产 spec"的工具——那种场景遇到
"没有 spec"，正确做法是**把它标记为 blocker 并停下**，而不是自动生成一份没人 review 的规格往下跑。

## 工作流程（阶段 0 + 四个工作阶段）

### 阶段 0 · 定位与上下文

1. **扫项目**：如果你还不了解代码库，先探索仓库理解当前状态——**测试怎么跑**
   （决定"成功标准"能落成什么形式的检查）、已有 spec / 文档、相关代码。脱离代码库的 spec 是愿望清单。
2. **接上游**：若存在需求概念文件（`docs/proposal/*` 或用户指明的位置），读入作为输入；
   没有，就做一次**轻量**意图确认（确认"要解决什么、不做什么"）。
   **若发现概念本身还没清**（连"要解决什么"都说不清）→ **停下来**，别用 spec 的外壳硬包一个没想透的想法。
3. **判 greenfield / brownfield**：
   - 新增能力 → 写全量 spec。
   - 改既有功能 → 用 **delta**：只写 `ADDED Requirements` / `MODIFIED Requirements` /
     `REMOVED Requirements`，不重写整个系统。
4. **判规模**：若这其实是多个独立能力，**先提示拆分**，逐个写 spec，别把一份 spec 撑成全系统说明书。

### 阶段 1 · 圈定能力维度并分级确认

阶段 2 的双探针抠的是"**选定要做的**需求，其边界与不做什么"（微观完整性）。但 greenfield 还有
一个更靠前的漏洞：**整类能力维度根本没被想到**（宏观全面性）。所以顺序是一个漏斗——
**先用 Coverage Map 圈定做哪些维度，再对纳入的维度用双探针抠边界。**

> **brownfield**：跳过调研与 Coverage Map——改动范围已被既有系统框定。只就**答案能改变
> spec 形状**的少数关键点（关键验收口径、需用户拍板的边界取舍、范围硬边界）确认式提问，
> 进 delta 起草。

**greenfield 分三步收敛，再起草：**

**1) 功能空间调研——调研与否由用户拍板（不是你）** —— greenfield 起草前，"要不要先做一轮
功能空间调研"是一个 **MUST 交给用户的决策**。你**主动、明确地问**，给出你的建议
（调研 / 跳过 + 一句理由），然后**停下等用户回答**，不得在用户表态前继续：

- 用户选**调研** → 用 **deep-research**：聚焦①领域常见能力维度②按丰富度分档③哪些易漏却会改变
  spec 形状。**铁律**：产出是**功能空间参考，不是需求**，一项都不默认纳入。
- 用户选**跳过**（或一开始就说了不调研）→ 凭需求 + 自身知识自列维度，spec 里注明"未调研"。
- **调研选了却跑不起来**（工具缺失 / workflow 失败 / 无网络）→ **不卡在反复重试**：如实告知
  "调研因 X 失败"，降级为凭领域知识自列维度（spec 注明"未调研：原因"），继续建 Coverage Map；
  是否另寻调研方式由用户定。
- 本次属于**有成熟功能空间、易漏整类能力**的领域（权限 / 通知 / SSH 运维 / 支付 / 导入导出…）时，
  调研价值高，**更要问**——别因"需求看起来够详尽"替用户跳过。

**2) 建 Coverage Map** —— 把"需求已含 + 调研补充"的能力维度汇成一张表，每行**必落一个档位**：

- **纳入** → 阶段 2 写成 Requirement + Scenario。
- **默认不做** → 写成 MUST NOT 或在覆盖表标注（可被 review 反对）。
- **后续版本** → 进覆盖表 + 待解问题。
- **必须确认** → 按第 3 步分级。

**不默认全纳入**——每行都有收敛决策。这是防 spec 从"全面"滑向"全行业功能大全"的唯一闸门。

**3) 分级确认（别一次抛几十个问题）** —— 对需澄清的点分三级：

- **现在问**：答案会改变 spec 结构（核心数据模型 / 主流程 / 范围硬边界）→ 现在聚焦提问，一次一问或小批量。
- **采用默认**：不影响主方向 → 记"采用保守默认：X"，不打断。
- **放 Open Questions**：重要但不阻塞本版 → 进 spec「待解问题」。

> 检验：「这个问题不问，spec 能不能起草？」能 → 它**不是**"现在问"。

列维度 / 判档 / 调研的完整清单见 [references/coverage-map.md](references/coverage-map.md)。

### 阶段 2 · 起草 spec（行为契约）

按 [references/spec-template.md](references/spec-template.md) 落盘。模板里已有各节的形状，
这里只给模板不含的判断规则：

- **行为需求**：Requirement + MUST/SHALL + 每条配 Scenario（`WHEN <触发> → THEN <可观察结果>`）。
  写不出可观察结果的（"系统应该很好用 / 性能要好"）是**愿望不是需求**，
  **打回重写成可观察的，或删掉**。
  > 检验：把 Scenario 交给一个不懂业务的人，他能照着判断"通过 / 不通过"吗？不能，就还没写清。

  brownfield 用 delta 标注。
- **不做什么（MUST NOT）**：概念里每条"不做什么"都转成负向需求，**每条配可验证检查**——
  写不出"怎么检查它没发生"的，说明边界还太虚，没转化完。
- **边界场景覆盖**（索引）：只写"要做什么"会漏掉一半真实需求——漏在边界上。用边界探针
  （边界值 / 空值 / 排序 / 并发 / 幂等 / 精度 / 编码 / 超时与失败）逐项自问"这条适用吗"，
  适用的写成 Scenario；本节只做覆盖核对，行为只写在 Scenario 里，不重复。
- **能力覆盖与档位**（greenfield）：把 Coverage Map 以精简表落盘，让 review 一眼看到
  哪些做 / 不做 / 为什么；纳入项对应到 Requirement。
- **成功标准**：可执行的检查，对应阶段 0 摸到的"测试怎么跑"。

两个探针的逐项清单、以及"怎么把每一项转成可验证的 Scenario / MUST NOT"（含"MUST NOT 的验证
优先写用户可观察行为、代码级检查只作辅助"这条规则），见
[references/coverage-probes.md](references/coverage-probes.md)——起草时逐项扫。

**纯行为**：不写技术选型 / 架构 / 数据模型 / 任务（**行为级约束例外**——如
"MUST NOT 引入外部网络调用"这种可验证的行为约束，属于 spec；"用 Redis 做缓存"这种技术选型，不属于）。

### 阶段 3 · 自检（落盘前过一遍）

1. **逐条过模板的「写完自查」**（[references/spec-template.md](references/spec-template.md) 末尾）。
2. **spec 卫生**：占位符 / TODO / 没写完的节 → 补全；自相矛盾（两条需求打架、Scenario 与
   Requirement 不一致）→ 修掉；歧义（任何一条能有两种解读）→ 选一种写死；范围过大 → 提议拆分。
3. **（greenfield）Coverage Map**：每行有唯一档位、无"待定"残留；"纳入"都成了 Requirement、
   关键"默认不做"都成了 MUST NOT；有没有把调研维度无脑全纳入（膨胀）。

**达标即停**：每条 Requirement 都有 Scenario、双探针都过、"不做什么"都成了可验证 MUST NOT、
成功标准可执行——spec 就够了，进入 review 门禁。别为"更完整"无限加需求，也别为"更全"把
"后续版本 / 默认不做"的维度硬塞进本版。就地修复，不必重复 review。

### 阶段 4 · 用户 review 门禁

1. **落盘**：把 spec 写入仓库（默认就写文件——spec 是要进仓库、实现期持续更新的工件）。
2. **请用户 review**，并明确这条规矩：
   > **未通过 review 的 spec，不得采用。**
3. 用户要改 → 回阶段 2 / 3 修订并重过自检；用户**显式确认** → 过门。
4. **过门后**：**不自动调用其他 skill、不开始写代码**。本 skill 到"规格确认"为止。

**哪些回答不算 "yes"**：

- "你看着办 / 都行" = 委托，不是决策。
- "听起来不错" = 模糊回应。
- 沉默后一句"那就开始吧" = 放弃，不是确认。

## 产物与落盘

- **默认单份文档**，内容是行为契约（Requirement / MUST / Scenario / MUST NOT / 边界 / 成功标准）。
- **位置**：跟随仓库既有 spec 约定——若已有 `docs/specs/`，就跟随；
  否则默认 `docs/specs/<YYYY-MM-DD>-<主题>-spec.md`（目录不存在先跟用户确认）。
- **brownfield** 用 delta，只写这次改了什么。
- 规模极大 / 多能力时，**可提议**拆成 per-capability 多文件，但这是 scale-up，不是默认。
- 参考：[spec-template.md](references/spec-template.md)（落盘模板，含 delta 写法与写完自查）、
  [coverage-probes.md](references/coverage-probes.md)（双探针逐项清单）、
  [coverage-map.md](references/coverage-map.md)（greenfield 能力覆盖图与定档）。

## 反例（不要这样做）

❌ 把概念单换种措辞抄一遍当 spec —— 没有 Scenario、不可验证。
❌ "不做什么"只写一句"不做同步"，没给"怎么验证它没发生"。
❌ 在 spec 里写"用 React + SQLite""加一个 Redis 缓存层"——越界到技术方案。
❌ （greenfield）自己判断"需求够详尽 / 已有发散材料"就跳过功能空间调研——跳不跳过是**用户的决策**，
必须主动问、等用户拍板（"你觉得需要再说"不算问）。
❌ （greenfield）只照需求明说的功能写 spec，整类能力维度（权限 / 空态 / 批量 / 导出…）静默漏掉。
❌ 把功能空间调研结果当需求，所有维度全纳入——spec 膨胀成"全行业功能大全"。
❌ 改一个小功能却重写整个系统的 spec —— 该用 delta。
❌ 动笔前不看代码、不看测试怎么跑，写出一份脱离代码库的愿望清单。
❌ 没落盘、没让用户 review 就说"spec 好了，开始写代码"。
❌ 概念其实还没想清，却用 spec 的外壳硬包着往下冲 —— 停下来。
❌ 在 CI / 自治循环里自动产 spec，没有活人 review。
