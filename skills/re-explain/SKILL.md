# Re-Explain — 重讲一遍

等一下，刚才那段没听懂。

**把它重讲一遍**——不是把原话再说一次，是换一条路径重新解释。

## 先判断卡在哪

重讲之前，先判断对方是卡在哪一层。三选一，只能选一个：

1. **不知道你在说什么事** —— 缺上文。他不知道这段话属于哪个问题、为什么现在讲它。
2. **知道是什么事，但听不懂内容** —— 句子太绕、术语太多、抽象度太高。
3. **听懂了，但不知道跟他有什么关系** —— 缺落点。不知道要他做什么、对他有什么影响。

用户点明了卡点（"第二段没懂""不知道你为什么要这么做"）就按他说的来，**只重讲那一段**。
判断不出来时，直接按第 1 类处理——补上文的代价最小。

**不要为了确认卡点而反问**。默认直接重讲。只有当上一条回复涉及多个互不相关的主题、
不问就无从下手时，才问一个问题。

## 重讲的结构

按这个顺序，四段，短：

1. **落点先行**：一句话说清这段在解决什么问题、为什么现在讲它。
2. **一句话结论**：把核心结论直接说出来，不铺垫、不推导。
3. **展开**：分点讲，每点一句话。只讲支撑结论必需的，其余全砍。
4. **一个具体例子**：用一个具体场景、一组具体数字或一段具体输入输出，把抽象说法落地。

## 简明中文（本 skill 的核心约束）

完整规则和病句对照见 `references/plain-chinese.md`。最要紧的六条：

1. **一句一个意思**，句子控制在 30 字以内。长句一律拆开。
2. **主动语态、动词打头**：写"系统会拒绝这个请求"，不写"该请求会被系统所拒绝"。
3. **一个概念只用一个词**：全程不换说法。不要一会儿"任务"、一会儿"作业"、一会儿"job"。
4. **拆开名词堆**：把"用户配置同步失败重试机制"改写成"同步用户配置失败后，会自动重试"。
5. **删掉模糊限定**："其实""基本上""某种程度上""可以认为"——这些词不承载信息，全删。
6. **先解释，再比喻**：比喻只能作为已经讲清楚之后的补充，不能代替解释。

## 术语沿用，不另造词

术语一律沿用项目里**已经在用**的说法。按顺序找：`CONTEXT.md`、`CLAUDE.md`、`AGENTS.md`、
`README.md`、术语表或词汇表、代码里的命名。

找不到既有说法时，用最普通的中文词，并明确说一句"这是我起的说法"。**不要为了显得准确
而发明新词**——听不懂的原因往往就是上一条回复里造了词。

英文缩写和外来术语首次出现时给一句中文解释；项目里通用的除外（如 API、CI）。

## 硬规则

1. **必须更短**：重讲版的字数要**明显少于**原文。讲不清是路径不对，不是篇幅不够。
2. **换路径，不换包装**：换一种解释方式（具体例子 / 反例 / 从后果倒推 / 拆成步骤 / 类比），
   不要把同样的话换几个同义词再说一遍。
3. **不辩解**：不要说"我上面说的意思是……""可能我表达得不够清楚"。直接重讲。
4. **不追加新信息**：只重讲已经说过的内容。想到了新东西，重讲完另起一段说。
5. **不降低准确性**：简化的是表达，不是事实。为了好懂而说错，比没讲清更糟。
6. **只重讲，不动手**：不要顺势开始改代码、写文件或执行刚才讨论的方案。

## 完成标准

- 说清了这段在解决什么问题，以及为什么现在讲它。
- 用了简明中文的六条，术语和项目里的说法对得上。
- 有一个具体例子。
- 比原文短。
- 事实没有被简化掉。

## 反例

- 把原话拆成条目符号，措辞照旧——那是重排版，不是重讲。
- 用同义词把每个术语再包一层，句子变长，理解成本更高。
- 先花两句解释"我刚才的意思是"，再重复一遍原话。
- 讲得更抽象了："本质上这是一个一致性问题"——听不懂的人更听不懂了。
- 为了好懂把条件砍掉，说成一个其实不成立的绝对结论。
- 重讲一半，顺手开始改代码。
