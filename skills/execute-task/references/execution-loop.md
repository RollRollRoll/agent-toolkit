# 每任务闭环 — 红 → 绿 TDD、小步、验证、证据、提交

> 用途：`execute-task` 招牌机制「核心一」的操作细则。阶段 2 每个任务内部怎么走。
>
> **闭环**：干净基线 → 主 agent **自己**在**已约定 seam** 上红 → 绿 → 小步实现 → 按验证方式验证 →
> 核证据过闸门一；checkbox 与代码一起 atomic commit。一个任务一个干净闭环。
>
> **任务内不派任何 subagent，也没有审查轮与修复轮**：质量由红 → 绿本身承担，闸门一的判据是
> **红 → 绿证据 + 验证全绿 + 范围没漂**——三样都可机械核对，不靠谁"看一遍觉得行"。
> 架构级审查集中在阶段 3 整体验收做一次（那里才派独立 subagent）。

## 一 · seam：测在哪，事先约定

- **seam** = 能从外部观察行为的公共边界（纯函数、模块接口、注入点）。测试住在 seam 上，不伸进内部实现。
- **不在未约定的 seam 上写测试**：seam 由 make-design / split-task 指定；tasks / design 没指明的任务，
  开工前把该任务的 seam 写下来**与用户确认**，再写进任务简报。
  测错地方比测得少更糟——任务内没有 reviewer 会替你发现测的是外壳还是内部实现。
- 难测的外壳（IO / 框架 / 网络）不硬测：把行为挤到 seam 内侧，外壳留薄。

## 二 · 什么是好测试

- **验行为，不验实现**：通过公共接口观察结果。实现可以整体改写，测试不该跟着改。
- **读起来像规格**：`test_empty`（空集合返回 `[]`）一眼看出存在什么能力——描述 WHAT，不是 HOW。
- **期望值来自独立事实来源**：已知字面量、手算样例、spec 里的精确值。
- **能活过重构**：只改结构不改行为时测试仍绿。测试因重构而红，说明它耦合了实现。
- **一个测试一个逻辑断言**：失败时能直接指出坏掉的是哪条行为。

## 三 · 三个反模式（任务内没有 reviewer，自己认出来）

- **实现耦合**：mock 内部协作者、测私有方法、断言调用次数 / 顺序、绕过被测接口从侧信道验证
  （建完用户直接查库断言那行存在）。可辨识信号：重构后测试红、但行为没变。
  → 从**同一个接口**读回来验（`createUser` 后用 `getUser` 取，断言取到的内容）。
- **同义反复**：期望值按代码的同一套算法重算一遍（`expect(calculateTotal(items)).toBe(items.reduce(...))`、
  按同样方式手推的快照、常量等于自己）。它按构造必然通过，永远不可能与代码不一致
  → 换成独立字面量（`toBe(15)`）。
- **水平切片**：先写完所有测试再写所有实现。批量测试验的是**想象中的行为**，验到的是结构的形状而非用户可见行为，
  对真实改动不敏感 → 走**垂直切片**：一个测试 → 一个最小实现 → 下一个；每个测试都是 **tracer bullet**，
  回应上一轮学到的东西。

## 四 · 循环规则

- **红先于绿**：先写失败测试，再写刚好让它过的实现。看到红时确认**失败原因是行为缺失**——
  语法错、import 错、环境没配好导致的红不算红过，先修掉再重跑。
- **一次一片**：一个 seam、一个测试、一个最小实现。不提前实现下一个测试要的东西、不加投机功能。
- **重构不进循环**：让测试转绿的那一步不顺手改结构。任务边界内的小整理，改完复跑覆盖测试；
  结构性问题写进执行记录的「疑虑」——留给阶段 3 的 architecture 轴，
  或退回 split-task 加任务，不在红绿之间夹带。
- **边做边留证据**：每转一次红或绿，**当场**把命令、输出、为何预期失败追加进
  `.execute-task/task-N-record.md`。跑完一整轮再凭印象补写的是回忆，不是证据；
  上下文被压缩后，只有落盘的那份还在。
- **mock 只在系统边界**：外部 API、时间 / 随机，（有时）数据库与文件系统。不 mock 自己的模块和内部协作者。
- **bug 类任务先写复现测试**：先用一个失败测试复现 bug，再修，让它转绿——保证修对了、且不回归。

## 五 · 小步推进

- 不一次写完整功能；不堆到约 100 行才第一次跑测试。
- **每一步保持系统可构建、可测**——随时能跑、能验证。
- 未完成但需合并的功能，用 **feature flag** 挡住，别让半成品阻塞主干。

## 六 · 验证节奏

按从快到慢分层验证，快的频繁跑：

- **typecheck**（若项目有）：改完随手跑，最快抓类型错。
- **单测文件**：跑当前任务相关的测试文件，确认这一片绿。
- **全套测试**：任务闭环末尾 / checkpoint 跑一次，确认没碰坏别处。
- 对齐任务的「验证方式」（split-task 已给，如 `pytest tests/test_x.py`）。

## 七 · 闸门一：核证据（跑命令与比对，不是代码审查）

红 → 绿走完先**别 commit**：证据已经在执行记录里，现在停下来核三件可机械判定的事。
自己做的活自己核，判据必须是**落盘的输出**，不是"我记得都跑绿了"：

1. **红 → 绿证据齐**：执行记录里每个行为都有实现前的失败输出（含"为何预期失败"）和实现后的通过输出，
   且都是当场写的。只有绿、没有红 → 这个行为没走成 TDD：把它**重做一遍红 → 绿**
   （必要时 `git stash` 掉该行为的实现，让测试真的红一次）；做不到就记录在案并告知用户，
   别拿事后补的测试冒充红证据。
2. **验证方式收尾实跑绿**：**完整跑一次**任务的验证命令（加 typecheck / 相关测试文件），看退出状态与输出，
   输出里的告警 / 噪音也要看见——不拿红绿循环中途某一次的输出顶替，那时的代码还不是要提交的代码。
3. **范围没漂**：`git rev-parse HEAD` 仍等于 `task-baseline.sh` 记录的基线（红绿途中没顺手 commit），
   `git status --porcelain=v1 --untracked-files=all` 的改动落在任务涉及的文件内。

三条齐 + 任务「验收标准」逐条对上 = **过闸门一**。任一条不齐 → **不 commit、不标 `[x]`**：
重做那一段红 → 绿，或按升级阶梯交用户判断。

## 八 · atomic commit

- **先有授权**：任何代码修改前，阶段 0 必须已获得用户对当前分支、tasks 范围和本批次提交的明确授权；
  拒绝 / 含糊就停止。每次 commit 前核对仍在授权范围内。
- **一个任务一个原子提交**：过闸门一后先把 tasks.md 对应项改成 `[x]`，将代码、测试和 checkbox 一起提交；
  提交粒度对齐任务，便于追溯与回滚。
- 提交信息可追溯到任务（如 `feat: list_experiments 查询+校验+稳定排序`）。
- **过了闸门一才提交**。提交成功后才写 ignored ledger，随后确认真实工作区干净；
  未干净不开始下一任务。

## 九 · bug 类任务的诊断（按需）

任务本身是修 bug 时，先诊断再改：

1. 建立**紧凑反馈循环**（能快速复现）。
2. **复现并最小化**问题。
3. 提 **3~5 个可证伪假设**。
4. **定向插桩**验证假设。
5. 写**回归测试**（复现测试），确认它红。
6. 修复到绿，并**清理调试代码**。

## 收尾自检

- 测试写在**已约定的 seam** 上？tasks / design 没指明的 seam 与用户确认过、写进简报了？
- 是垂直切片（一个测试 → 一个最小实现 → 下一个）而非先写完所有测试？每一轮的红都确认过失败原因是行为缺失？
- 期望值来自独立字面量 / spec，不是按代码算法重算？mock 只在系统边界，没 mock 自己的模块？
- 让测试转绿的那一步没夹带重构？看到的结构问题写进疑虑而不是顺手改了？
- 每转一次红 / 绿都**当场**把命令与输出写进了 `.execute-task/task-N-record.md`，不是事后追写？
- bug 任务先写了复现测试？小步推进、每步可构建可测？
- 验证按 typecheck → 单测 → 全套分层跑了？对齐任务验证方式？
- 过闸门一核了三样：**红 → 绿证据齐**、收尾完整跑一次验证命令绿、HEAD 未漂移且改动范围没越界？
- 过闸门一才 atomic commit？提交在用户授权内且包含代码 / 测试 / checkbox？提交后才写 ledger 并确认 clean？
