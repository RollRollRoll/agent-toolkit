# 模型选择 — 派发 subagent 时按角色与复杂度定档

> 用途：阶段 2 派发执行 subagent，阶段 3 派发整体验收 review / fix 时，据此选模型档位。
> 目标：用够用的最省档位控成本、提速度；但**轮次数比单价更影响总成本**——档位选错反而更贵。
> 前提变了要知道：**任务内已没有独立 reviewer 兜底**，执行档位选低的代价不再是"多修一轮"，
> 而是"缺陷带着一堆绿测试进 commit"——所以执行档位比过去更该往上取。

## 一 · 铁律

- **派发时必须显式指定模型**——不写等于让 subagent 继承主 agent 当前档位（通常是最贵最强档），
  悄悄废掉分档的意义。
- 三档：**cheap（便宜档）/ standard（标准档）/ most-capable（最强档）**——具体对应平台上哪个模型，
  由当前平台与账号实际可用模型决定，不在此写死。平台参数映射见 [platform-agents.md](platform-agents.md)。

## 二 · 按角色定档

| 派发对象 | 默认档位依据 | 升档信号 |
|---|---|---|
| 执行 subagent（阶段 2 唯一派发） | 默认 **standard** 兜底：它同时要写测试和实现，且没人复核 | 需要架构判断或读懂大范围既有代码 → **most-capable**（少见——设计本该已在 make-design 锁定，出现即提示上游可能漏了决策，别把它当常态） |
| 阶段 3 整体验收（whole-branch review） | 固定 **most-capable**——不用 session 默认档位，这是全链路唯一的架构级判断点 | — |
| 阶段 3 fix subagent | 与整体验收发现的复杂度匹配，通常 **standard**；涉及并发 / 状态机 / 安全边界 → **most-capable** | 复审仍不过、问题涉及原设计 → 停下退回上游，不是无限升档硬修 |

## 三 · cheap 档的适用面（比过去窄）

**只有"转录类"任务才用 cheap**：简报里已给出可直接照抄的完整代码 / 完整测试用例，且是单文件机械修改——
执行方不需要判断力，只需转录 + 跑测试。

其余一律 **standard 起**：按文字描述实现、需要自己拼装多文件、需要自己设计测试用例——
这些地方过去由 reviewer 兜住，现在没有了。

## 四 · 轮次数比单价更重要

- 便宜档在多步任务上经常要 2-3 倍轮次，折算下来不一定省。
- 更贵的是**看不见的返工**：cheap 档写出同义反复测试或测在实现细节上，测试全绿、闸门一也过得去，
  等到阶段 3 才被审出来，返工范围已经是整条分支。

## 派发前自查

- 每次派发都**显式指定了模型与必要的推理档位**（Claude Code 用 Agent `model`；Codex 用 agent 配置或派发时支持的 model / reasoning 参数），没有留空任其继承主 agent？
- 执行档位默认取了 standard？用 cheap 时确认过它是"简报里已给完整代码的单文件转录类"任务？
- 阶段 3 整体验收固定用了 most-capable，没有沿用 session 默认档位？
